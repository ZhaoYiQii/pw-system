# 微信支付（服务商模式）多商户接入设计 v1

日期：2026-09-23 ｜ 状态：**待用户确认**（服务商入驻与公众号认证已在办，1–2 天出结果）
相关：`docs/superpowers/plans/2026-09-22-third-party-integrations.md`（S4 契约核对）

## 0. 一屏结论

- **通道**：微信支付**服务商模式** + **JSAPI**（`sp_appid` + `sp_mchid` + `sub_mchid` + `payer.sp_openid`）。
- **门店不需要**：自己的公众号、微信认证、网页授权域名配置、自己的支付凭证。门店只做两件事：**提供进件资料** + **老板扫码完成开户意愿确认**。
- **资金路径**：钱**直接进门店的子商户号**；平台不经手、不抽成（`finance_rate_rules.platform_fee_bp` 默认 0，ADR-0004）→ 不触碰二清。
- **全自动记账**：支付回调自动入账 + 幂等 + 每日拉账单对账 + 出账记账 + 退款，全程无需人工登记。
- **平台侧只有一套凭证**（服务商商户号 + 服务商公众号），配一次，服务所有门店。

## 1. 范围与非目标

**做**：服务商凭证装配、JSAPI 下单与调起、支付回调（验签+解密+幂等+入账）、每日账单对账、退款与退款回调入账、门店进件与开户意愿确认、门店支付状态展示。

**不做**：平台代收（二清）、平台抽成与分账、聚合支付第三方通道、H5 支付（个体工商户不支持，官方主体表已核）、Native 扫码（线下场景，仅作兜底备选）。

## 2. 角色与资金流

```
客户（老板，微信内打开 H5）
   │ 1. 下单 → 平台 API（用服务商凭证向微信支付下单）
   ▼
微信支付（sp_mchid 代 sub_mchid 收单）
   │ 2. 调起 JSAPI 收银台（appId = 服务商 sp_appid，openid = sp_openid）
   │ 3. 支付成功 → 回调平台 notify_url
   ▼
平台：验签 → 解密 → 幂等 → 入账（门店账本 / 客户余额 / 订单状态）→ Outbox 通知
   ▲
   │ 4. 次日拉账单对账（按子商户）
资金：直接进门店的 sub_mchid 结算账户（平台不碰钱）
```

## 4. 数据模型（新增 / 扩展）

**平台级凭证不入库**（服务商模式只有一套）：`sp_mchid`/`sp_appid`/APIv3 密钥/商户私钥走环境变量与挂载文件（`D:\pw system\secrets\`，`.gitignore` 已覆盖 `*.pem`/`*.key`/`.env.*`）。这是服务商模式相对"多商户直连"的又一处简化：**门店级凭证不需要存储**。

| 表                                                               | 用途                           | 关键字段                                                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tenant_payment_accounts`（新）                                  | 门店作为子商户的状态           | `tenantId`(unique)、`subMchid`、`subAppid?`、`applyNo`、`status`(APPLYING/PENDING_CONFIRM/ACTIVE/SUSPENDED)、`lastSyncedAt`                        |
| `payment_orders`（扩展）                                         | 支付单                         | 现有 `tenantId/outNo/amountFen/provider/providerRef/status` + 新增 `spMchid`、`subMchid`、`payerOpenidEnc?`、`prepayId`、`transactionId`、`paidAt` |
| `payment_refunds`（新）                                          | 退款单                         | `outRefundNo`(unique)、`paymentOrderId`、`amountFen`、`status`、`refundId`                                                                         |
| `webhook_inbox`（新）                                            | **回调先落库再应答**（防丢单） | `provider`、`eventId`(unique)、`headers`、`rawBody`、`signatureVerified`、`processedAt`                                                            |
| `reconciliation_statements` / `reconciliation_differences`（新） | 对账文件与差异                 | 账单日期、`subMchid`、文件摘要、差异类型（本地缺/微信缺/金额不符）                                                                                 |

已有可复用：`idempotency_records`（幂等）、`ledger_*` / `earnings` / `settlements`（记账与结算）、Outbox（通知）、`finance_rate_rules`（平台费 0）。

## 5. 状态机与幂等

- **支付单**：`CREATED → PREPAID（拿到 prepay_id，2 小时有效）→ PAID（回调确认）`；超时未付 → `CLOSED`（调关闭订单接口）或 `EXPIRED`（`time_expire` 只是不能再付，**不等于关单**）。
- **订单/余额联动**：`PAID` → 事务内 ① 写 `ledger_*` ② 更新订单状态 ③ 客户钱包/余额入账（若走钱包）④ Outbox 发通知。
- **幂等键**：下单用 `out_trade_no`（= `payment_orders.outNo`，已按租户唯一）；回调按 `transaction_id` + `out_trade_no`；退款用 `out_refund_no`。
- **金额校验**：回调金额必须等于 `payment_orders.amountFen`，否则**不入账**，写对账差异并告警。

## 6. 关键实现要点（踩坑清单）

1. **回调 5 秒预算**：先验签 → **把原始报文写入 `webhook_inbox`** → 应答 200 → 再由 worker 解密与入账。这样即使进程崩溃也不会丢单（微信重试只有 15 次）。
2. **openid 来源**：`sp_openid` 必须来自**服务商自己的公众号**（网页授权） → S3 已实现的网页授权/state/回调代码**可直接复用**，只需把配置换成服务商的 AppID/AppSecret，并把「网页授权域名」配成我们的 H5 域名。服务商模式让"一个公众号服务所有门店"成立，正好契合 S3 的现状设计。
3. **证书轮换**：验签要按回调头 `Wechatpay-Serial` 选证书，支持平台证书 + 微信支付公钥**双来源并行**（公钥永久、平台证书 5 年）。
4. **对账**：每日按子商户拉账单 → 与本地支付的 `transaction_id/amount/state` 比对 → 差异入表；**漏单自动补记（标记来源=对账）**，本地多出的挂人工核查。
5. **退款**：申请前校验可退金额（含部分退款累计），退款回调同样走"验签 → 落库 → 应答 → 异步入账"。
6. **门店未完成开户意愿确认前不可收款**：进件成功 ≠ 可用；界面上必须显示 `PENDING_CONFIRM` 状态并给出"让老板扫码确认"的引导。
7. **PII 与日志**：`openid`/手机号脱敏；密钥、证书内容、`Authorization` 头永不进日志（S3 已建立该口径）。

## 7. H5 侧改动

- 下单：`POST /api/v1/tenant/payments/prepay { orderId }`（服务端按门店取 `sub_mchid` 下单）→ 返回 `{appId, timeStamp, nonceStr, package, signType, paySign}`。
- 调起：`WeixinJSBridge.invoke('getBrandWCPayRequest', params)`；不依赖前端回调，**支付结果以服务端订单状态为准**（轮询/推送）。
- 支付结果页：轮询 `GET /api/v1/tenant/orders/:id` 直到 `PAID`（或超时提示"支付结果确认中"）。

## 8. 门店接入流程（写进《门店接入说明》，给门店照着做）

1. 提供进件资料：营业执照（个体户也行）、法人/经营者身份证、结算账户、门店基本信息。
2. 平台提交进件（后续可做成后台自助表单）。
3. 微信审核 → 门店老板**扫码完成开户意愿确认**（官方要求，必要前提）。
4. 完成后门店可收款；平台后台显示状态流转（`APPLYING → PENDING_CONFIRM → ACTIVE`）。

## 11. 验收

**本机可验（零凭证）**：签名/验签/解密固定向量；回调幂等（同事件重复投递只入账一次）；金额不符拒绝入账；账单文件解析与差异识别；状态机流转；缺凭证启动即失败。

**需真凭证**：真实下单与支付、真实回调、真实退款、真实账单下载、门店进件与开户意愿确认。判据：微信返回的 `prepay_id`、回调事件入库与我方入账一致、账单金额与本地账本一致。

## 12. 风险与未验证

- **服务商资质审核结果未定**（在办）：审核口径与时长以微信支付页面为准。
- **开户意愿确认是收款前提**：门店老板不扫码 → 该店收不了钱；试运营前必须完成。
- **费率由门店签约类目决定**（常见 0.6%，以子商户签约费率页为准），平台不参与分成。
- **未逐页核实**：服务商侧退款/账单/进件的**字段级**细节（下单页已核 `sp_appid/sp_mchid/sub_mchid/sp_openid`）；实现该片前逐页从 `llms.txt` 取 `.md` 核对，不凭记忆写字段。
- **证书策略**：平台证书 5 年 / 微信支付公钥永久，需支持双来源并行验签与轮换。
