# 多游戏派单与模板中心 v2 — 设计规格

- 状态：通用模板架构修订及书面规格已批准，进入 S1b 实施计划
- 日期：2026-09-14
- 范围：订单中心的新建派单、游戏派单模板管理及其服务端接口
- 核心决策：采用“游戏 → 通用模板 → 草稿 → 已发布版本 → 派单快照”的模型；模板由通用字段、区块和可重复表格组成，岗位与段位仅作为参考预设，派单文案由发布快照和订单值自动生成；保存草稿不会影响新建派单，发布后才生效

## 1. 背景与问题

当前模板是租户级平铺资源，没有明确归属游戏。门店同时经营多个游戏时存在以下缺陷：

1. 模板列表只能靠名称识别，无法稳定筛选、分组或限制适用范围。
2. 新建派单缺少明确的游戏上下文，容易选择错误模板。
3. 模式、段位等业务行为依赖字段名或 fieldKey 字符串猜测，改名可能使规则失效。
4. 模板保存后立即影响后续派单，缺少草稿、发布、历史版本和恢复机制。
5. 切换模板可能丢失填写内容，且缺少明确告警和会话内恢复。
6. 列表加载完整模板详情，数据量增长后会产生多余查询和传输。
7. 编辑没有乐观锁，两个管理员可能相互覆盖。
8. 编辑器和真实派单对列数、另起一行、必填、启用等规则可能产生表现差异。
9. 岗位席位、段位加价和复制文案被建模为三个固定模块；启用状态与“数组是否为空”混在一起，禁用会丢失配置，且不同游戏无法自由组合两到五个甚至更多内容模块。
10. 段位加价只能表达一个固定维度，无法复用于地图、模式、时段、难度等其他价格调整维度。
11. 复制文案需要在每个模板中逐行维护字段映射，重复配置且容易与实际模板内容失去同步。

## 2. 目标与成功标准

### 2.1 目标

- 每个模板明确归属一个游戏；新建派单先确定游戏，再选择该游戏的模板。
- 模板编辑采用草稿与发布分离，线上派单只使用不可变的已发布版本。
- 使用明确的语义角色驱动模式、段位、时长等业务逻辑，不再依赖名称猜测。
- 支持筛选、复制、版本历史、恢复、归档和并发冲突处理。
- 编辑器、预览和新建派单共用同一套表单解释与渲染规则。
- 模板内容由通用区块、字段、说明和可重复表格组成，不向用户暴露固定的岗位、段位或复制文案模块。
- 岗位与人数、段位价格等常用结构仅作为可编辑的参考预设；加入后与普通模板内容完全一致。
- 任意选择类字段可配置选项价格调整，任意模板可明确配置人数来源。
- 所有派单统一根据已发布模板快照和实际填写值生成可复制文案，不再逐模板维护复制行。
- 旧订单保持可追溯，迁移过程可灰度、可回退。

### 2.2 成功标准

- 游戏 A 的派单无法选择游戏 B 的模板。
- 保存草稿后，现有线上版本不变；发布后新派单才使用新版本。
- 新订单记录准确的 gameId、templateId、templateVersionId 和模板快照。
- 修改字段显示名称不会破坏依赖语义角色的规则。
- 一个游戏可只使用两个内容区块，也可使用四至五个或更多区块，不受固定模块数量限制。
- 禁用区块或字段会保留其草稿配置；重新启用后内容恢复，只有显式删除才移除配置。
- 地图、模式、段位、时段或其他选择字段均可独立配置选项价格调整，不依赖“段位”名称。
- 任意已创建派单都能按订单快照自动生成与当前填写内容一致的文案表格和纯文本。
- 两人同时编辑时，旧修订提交返回冲突，不静默覆盖。
- 切换模板前提示已有输入，并能恢复本次弹窗会话内的填写内容。
- 旧订单展示不依赖模板当前状态或当前内容。

## 3. 非目标

本期不包含：

- 跨租户模板市场、公开分享或模板继承。
- 任意像素级拖拽画布。
- 计价引擎、支付流程或订单状态机重构。
- 移动端模板编辑器。
- 自动根据旧模板名称猜测所属游戏。
- 改写历史订单快照。
- 任意脚本、公式语言、自定义 SQL 或可执行低代码工作流。
- 允许租户通过字段名称隐式决定人数、金额或其他业务计算。
- 第一阶段不提供自由排版的文案模板语言、逐模板字段映射或门店级头尾文案设置；仅提供安全、确定性的自动文案生成。

## 4. 角色与权限

| 权限键               | 用途                       |
| -------------------- | -------------------------- |
| gameDispatch.create  | 使用已发布模板创建派单     |
| gameTemplate.view    | 查看模板和版本历史         |
| gameTemplate.edit    | 新建、复制和编辑草稿       |
| gameTemplate.publish | 发布及从历史版本恢复为草稿 |
| gameTemplate.archive | 归档、取消归档及受限删除   |

- Owner、Admin 默认拥有全部权限。
- 客服/操作员默认只拥有 gameDispatch.create 和 gameTemplate.view。
- 其他角色必须由门店权限配置显式授权，前端不得按角色名称硬编码。
- 服务端执行相同权限校验；隐藏按钮不是权限边界。

## 5. 核心领域决策

1. 复用现有 Game 实体，不建立第二套游戏字典。
2. 一个模板只归属一个游戏；跨游戏复用通过“复制到目标游戏”完成。
3. 模板主记录承载可编辑草稿，已发布版本是不可变快照；草稿内容是有序的通用区块与组件树。
4. 一个模板最多有一个当前生效版本，同时保留全部历史发布版本。
5. 已发布模板继续编辑时，线上仍使用旧版本；再次发布后才切换。
6. 订单保存版本标识和配置快照，模板归档或修改不影响历史订单。
7. 业务字段和可重复表格列使用 semanticRole 明确用途，不再模糊匹配名称或 fieldKey。
8. 草稿使用整份文档提交和 revision 乐观锁。
9. 从未发布且从未被引用的模板允许硬删除；其他模板只能归档。
10. 每个游戏最多一个默认模板，由服务校验和数据库部分唯一索引共同保证。
11. 岗位席位和段位加价不是领域模块，只是可以插入并继续修改的参考预设。
12. 人数规则通过 staffingSource 显式绑定为固定人数、数字字段或可重复表格数量列汇总；未配置时默认一人。
13. 价格调整绑定在选择字段的具体选项上，金额以整数分保存并由服务端基于发布快照计算。
14. 新发布版本不保存人工 copyLines；文案由通用渲染器按发布快照顺序自动生成。
15. 启用、禁用和删除是不同操作：禁用保留草稿内容，删除才移除定义。

## 6. 数据模型

### 6.1 模板主表扩展

| 字段                  | 说明                           |
| --------------------- | ------------------------------ |
| gameId                | 所属游戏；扩展迁移阶段允许为空 |
| description           | 模板用途说明                   |
| status                | DRAFT、PUBLISHED、ARCHIVED     |
| activeVersionId       | 当前生效的发布版本             |
| revision              | 草稿修订号，成功保存后递增     |
| isDefault             | 是否为该游戏默认模板           |
| lastUsedAt            | 最近用于派单的时间             |
| createdBy / updatedBy | 创建人和最近编辑人             |
| archivedAt            | 归档时间                       |

约束与索引：

- 同租户、同游戏下模板名称唯一：tenantId + gameId + normalizedName。
- 列表索引：tenantId + gameId + status + updatedAt。
- 对 tenantId + gameId 建立 isDefault 为真且未归档条件下的部分唯一索引。
- 外键关系必须验证租户一致性。

### 6.2 发布版本表

新增 game_dispatch_template_versions：

| 字段                       | 说明                     |
| -------------------------- | ------------------------ |
| id / tenantId / templateId | 版本、租户和模板标识     |
| versionNo                  | 模板内递增版本号         |
| configJson                 | 完整、不可变的发布配置   |
| changeNote                 | 发布说明                 |
| publishedBy / publishedAt  | 发布人和发布时间         |
| sourceVersionId            | 从历史版本恢复时记录来源 |

唯一约束：tenantId + templateId + versionNo。

### 6.3 通用草稿组件

草稿不再由岗位、段位和文案三种固定子模块组成，而是保存有序区块和通用组件。保存整份草稿必须在单一事务中完成。

支持的组件类型：

- FIELD：文本、数字、金额、日期时间、单选、多选、下拉等普通字段。
- REPEATABLE_TABLE：用户可增减数据行的可重复表格，每列有名称、控件类型、必填、选项和语义角色。
- NOTE：只读说明文字，只允许纯文本。

区块和组件共有以下属性：

- stableKey：发布版本内稳定引用，不允许通过显示名称参与业务计算。
- label、description：展示名称和说明。
- enabled：独立启用状态；禁用不删除配置。
- sortOrder：模板内顺序。
- layout：列宽、另起一行、密度和对齐等受控布局。

区块包含一个或多个组件。模板可以只有两个区块，也可以有四至五个或更多区块；服务端设置合理上限，避免无限文档和拒绝服务风险。

S1b 采用版本化整文档 JSONB 承载通用草稿，不为每一种动态组件创建独立业务表：

| 表                               | 新增字段                 | 类型与用途                                              |
| -------------------------------- | ------------------------ | ------------------------------------------------------- |
| game_dispatch_templates          | draft_config_json        | JSONB，可空；保存 schemaVersion 2 的完整通用草稿        |
| game_dispatch_templates          | draft_schema_version     | integer，可空；当前通用草稿固定为 2                     |
| game_dispatch_templates          | legacy_conversion_state  | text；NOT_REQUIRED、READY、NEEDS_REVIEW                 |
| game_dispatch_templates          | legacy_conversion_issues | JSONB；只保存结构化问题码和 stableKey，不保存敏感表单值 |
| game_dispatch_template_snapshots | config_json              | JSONB，可空；保存订单锁定的完整 schemaVersion 2 配置    |
| game_dispatch_template_snapshots | schema_version           | integer，可空；旧快照为空，新快照固定为 2               |

选择 JSONB 的原因是草稿本来就采用整份文档和 revision 乐观锁保存，组件结构是有判别字段的版本化联合类型，且列表、筛选和关联查询只依赖模板主表的关系字段，不需要查询 JSON 内部属性。S1b 不增加 GIN 索引；若未来出现已证明的 JSON 内部查询，再单独设计表达式索引。

数据库约束：

- draft_config_json 为空时 draft_schema_version 必须为空；非空时必须为 JSON object 且 draft_schema_version = 2。
- config_json 为空时 schema_version 必须为空；非空时必须为 JSON object 且 schema_version = 2。
- legacy_conversion_state 使用 CHECK 约束限制到三个允许值。
- 新增列不改变现有外键；模板和快照继续使用已有 tenantId 复合约束、索引和强制 RLS。
- 已执行的 S1 迁移不可修改，S1b 使用新的 expand 迁移添加可空列与 NOT VALID 检查，再验证约束。

服务端输入上限：

- 每个模板最多 20 个区块、100 个组件。
- 每个可重复表格最多 10 列、50 个默认行；每笔订单每个表格最多提交 50 行。
- stableKey 匹配小写字母开头、后接小写字母/数字/下划线且总长不超过 64；同一模板内唯一。
- 区块名、组件名和列名最长 50 个字符；说明和占位文字最长 500 个字符。
- 单个选择字段最多 100 个选项；整个草稿序列化后最大 256 KiB。

### 6.4 语义角色与业务绑定

语义角色属于通用字段或可重复表格列，不对应固定视觉模块。首批角色包括：

- CUSTOM
- MODE
- TARGET_RANK
- CURRENT_RANK
- DURATION_MINUTES
- SERVER_REGION
- CONTACT
- ORDER_NOTE
- STAFFING_LABEL
- STAFFING_COUNT

除 CUSTOM 外，同一发布模板中要求唯一的角色必须通过服务端校验。显示名称可以任意修改，不改变业务绑定。

模板级 staffingSource 明确人数来源：

- FIXED：固定需要人数，默认值为 1。
- NUMBER_FIELD：绑定一个启用的数字字段。
- REPEATABLE_TABLE_SUM：绑定一个启用的可重复表格及其 STAFFING_COUNT 数量列，并对所有有效行求和。

发布时校验引用存在、组件已启用、类型匹配、人数为正整数且不超过系统上限。新建派单只接受发布版本声明的人数来源，不根据“岗位”“人数”等文字猜测。

### 6.5 通用价格调整

任意单选、下拉或多选字段的选项可以包含 priceDeltaFen。它可以表达段位、地图、模式、时段、难度或其他维度的价格变化。

- priceDeltaFen 使用整数分的十进制字符串。
- 未配置时视为 0。
- 服务端只根据发布快照中选中的有效选项计算，不接受客户端提交最终价格。
- 多选字段是否累加必须由字段的明确 aggregationPolicy 决定；首版只允许 SUM 或 MAX。
- 价格调整不会修改历史订单价格快照。

“段位加价”参考预设只是创建一个带选项价格的选择字段，创建后可改名、改选项、关闭价格调整或删除。

### 6.6 参考预设

参考预设只在编辑器中帮助快速创建通用组件，不是运行时模块，也不在发布配置中保留特殊模块身份。

首批预设：

- 岗位与人数：创建一个可重复表格，并默认提供 STAFFING_LABEL 与 STAFFING_COUNT 两列，同时把 staffingSource 绑定到数量列汇总。
- 选择项加价：创建一个带选项价格调整的选择字段，可改名为段位、地图、模式或其他维度。

插入预设后，其区块、字段、列、选项、名称、顺序和启用状态都能继续编辑。删除预设生成的内容与删除普通组件相同。

### 6.7 自动文案与发布快照

configJson 包含 schemaVersion，以及模板和游戏标识、区块、通用组件、布局、选项价格、staffingSource、验证规则和安全展示元数据。服务端仅接受明确支持的 schemaVersion。

新发布版本不要求人工配置 copyLines。统一文案渲染器基于订单保存的发布配置快照和实际值生成：

- 结构化文案表格：字段显示名称与格式化后的值。
- 纯文本文案：按区块和组件顺序生成，可直接复制。

生成规则：

- 仅包含发布快照中已启用的区块和组件。
- 默认跳过没有填写的非必填字段，保留必填字段的明确缺失错误。
- 可重复表格按行输出，不暴露 stableKey、semanticRole 等内部标识。
- 文案内容进行纯文本转义和长度限制，不接受自定义 HTML、脚本或任意模板表达式。
- 历史订单始终使用订单自身快照生成，当前模板后续修改不影响历史文案。
- 文案格式由服务端 documentRendererVersion 固定版本控制；第一阶段不提供逐模板 copyLines 编辑器或可编辑模板表达式。

## 7. 生命周期

### 7.1 新建与保存

- 新模板状态为 DRAFT，没有 activeVersionId，不能用于新建派单。
- 保存草稿时提交完整草稿和 expectedRevision。
- 服务端事务校验并保存，随后 revision 加一。
- 保存不改变 activeVersionId。

### 7.2 发布与再编辑

- 发布前执行结构、语义、组件引用、人数来源、选项价格和权限校验。
- 发布事务生成不可变版本、递增 versionNo，并更新 activeVersionId 和状态。
- 新派单使用新版本；已经打开的派单保持其锁定版本。只要模板未归档，服务端允许其按锁定的旧发布版本提交，不静默升级。
- 已发布模板可以继续编辑草稿，界面同时显示线上版本和草稿修订。

### 7.3 归档、恢复与冲突

- 归档后模板不再出现在新建派单列表，历史订单和版本保持可读。
- 取消归档时，有 activeVersionId 的模板恢复为 PUBLISHED，没有 activeVersionId 的模板恢复为 DRAFT。
- 恢复历史版本会将其克隆为新草稿，检查并再次发布后才上线。
- expectedRevision 不一致时返回 409 TEMPLATE_REVISION_CONFLICT，并携带当前修订、编辑人和更新时间。
- 客户端保留本地内容，提供“重新加载”和“复制我的内容”，不自动覆盖。

## 8. API 设计

### 8.1 模板管理

- GET /api/game-dispatch-templates?gameId=&status=&q=&sort=&cursor=
  - 只返回列表摘要，不组装完整详情。
- POST /api/game-dispatch-templates
  - 在指定游戏下创建草稿。
- GET /api/game-dispatch-templates/:id/draft
  - 返回草稿、修订号和生效版本摘要。
- PATCH /api/game-dispatch-templates/:id/draft
  - 提交完整草稿和 expectedRevision。
- POST /api/game-dispatch-templates/:id/publish
  - 提交 expectedRevision 和 changeNote 并发布。
- GET /api/game-dispatch-templates/:id/versions?cursor=
- POST /api/game-dispatch-templates/:id/restore
- POST /api/game-dispatch-templates/:id/copy
  - 必须提供 targetGameId 和 newName。
- POST /api/game-dispatch-templates/:id/archive
- POST /api/game-dispatch-templates/:id/unarchive
- DELETE /api/game-dispatch-templates/:id
  - 仅限从未发布且未被引用的模板。

### 8.2 新建派单

- GET /api/games/:gameId/dispatch-templates
  - 只返回未归档且有生效版本的模板摘要。
- GET /api/game-dispatch-template-versions/:versionId/form
  - 返回派单使用的发布配置。
- POST /api/game-dispatch-orders
  - 必须提交 gameId、templateId、templateVersionId、通用组件值和 idempotencyKey。

服务端验证游戏、模板、版本的租户和归属关系；只接受发布配置中的启用组件；按发布版本验证必填、类型、选项、可重复表格、人数来源和价格调整；相同 idempotencyKey 不创建重复订单。

### 8.3 schemaVersion 2 契约

DraftConfigV2 和 PublishedConfigV2 使用判别联合，顶层字段固定为：

- schemaVersion：固定为 2。
- sections：有序区块数组。
- components：FIELD、REPEATABLE_TABLE、NOTE 的有序联合数组，每项通过 sectionKey 归属区块。
- staffingSource：FIXED、NUMBER_FIELD 或 REPEATABLE_TABLE_SUM 的联合对象。

PublishedConfigV2 在草稿字段之外由服务端增加 documentRendererVersion，用于保证同一发布版本的自动文案格式可确定性重建；客户端不能修改该值。

组件值通过 stableKey 提交：

- FIELD：字符串、字符串数组或整数，具体类型由发布配置决定。
- REPEATABLE_TABLE：对象数组；每行的列值按 column stableKey 提交。
- NOTE：不接收订单值。

关键请求与响应：

- 创建模板请求：gameId、name、description；响应为模板摘要和初始 revision。
- 保存草稿请求：expectedRevision、config；响应为新 revision、updatedAt、updatedBy 和结构化 validationWarnings。
- 发布请求：expectedRevision、changeNote；响应为不可变 versionId、versionNo、publishedAt 和模板摘要。
- 获取派单表单响应：templateId、gameId、versionId、versionNo、config。
- 创建派单请求：gameId、templateId、templateVersionId、values；Idempotency-Key 由请求头提供并跨同一意图重试复用。
- 创建派单响应：orderId、dispatchOrderId、templateVersionId、staffingSummary、priceAdjustmentFen 和自动文案摘要。
- 获取订单文案响应：schemaVersion、rows、plainText、generatedFromSnapshotAt；不返回内部 semanticRole 或数据库列名。

兼容规则：

- 现有 schemaVersion 1 版本和旧摘要字段只读保留，不改变已公开字段类型。
- v2 新字段以新增方式提供；旧接口在灰度期继续返回旧结构，不能把同一路径的响应静默改成不兼容形状。
- 服务端根据 schemaVersion 选择显式解析器，不允许把未知版本当作最新版。
- 同一 Idempotency-Key 携带不同请求体返回 422；正在处理的重复请求返回 409；已成功请求返回原结果。

结构化错误继续使用项目统一问题响应：

- 409 TEMPLATE_REVISION_CONFLICT：expectedRevision 已过期。
- 409 TEMPLATE_ARCHIVED：填写期间模板被归档；页面保留用户值并要求重新选择。
- 422 TEMPLATE_VERSION_UNAVAILABLE：版本不存在、不属于该模板或 schemaVersion 不受支持；已经打开并锁定的合法历史发布版本仍按第 7.2 节允许提交。
- 422 TEMPLATE_COMPONENT_INVALID：组件结构、类型或数量越界。
- 422 TEMPLATE_BINDING_INVALID：人数来源或其他 stableKey 引用无效。
- 422 TEMPLATE_PRICE_RULE_INVALID：选项金额或聚合策略无效。
- 422 TEMPLATE_LEGACY_REVIEW_REQUIRED：旧价格规则尚未完成人工确认。

所有字段长度、判别类型、金额、数组上限和额外字段拒绝均在 API 边界通过版本化 Zod schema 执行；领域层接收验证后的类型，不重复解析不可信 JSON。

## 9. 模板管理交互

### 9.1 信息架构

页面顶部提供游戏筛选、状态筛选、搜索、排序和“新建模板”。游戏筛选包含“全部”“未归类”和租户拥有的游戏；状态包含草稿、已发布、有未发布改动、已归档。

列表卡片显示模板名、状态、线上版本、草稿更新时间、编辑人、最近使用和默认状态。筛选、搜索、模板标识与编辑标签写入 URL，刷新和分享链接后可恢复。

### 9.2 编辑器

编辑区分为三个标签：

1. 内容设计
2. 业务绑定与计算
3. 发布设置与版本历史

固定主要操作为“保存草稿”“预览草稿”“发布”。复制、设默认、归档和删除进入次级菜单。发布按钮仅对有权限且校验通过的用户可用。

### 9.3 通用内容设计

- 区块先定义每行列数，字段再定义占用列数或整行。
- “半宽”“整行”等标签按真实列数计算，不显示静态文案。
- 拖动排序和键盘上移、下移得到相同结果。
- 每个区块、字段、说明和可重复表格卡片直接展示启用开关、必填、另起一行和列宽状态。
- 启用开关与删除按钮分离；关闭开关时卡片保留并弱化显示，重新开启恢复原配置。
- 设计器网格的空位显示“添加内容”卡片，可以添加普通字段、可重复表格、说明、新分区或从参考预设添加。
- 可重复表格支持增删列、配置列类型、增删默认行和绑定列语义角色。
- “岗位与人数”“选择项加价”只出现在参考预设菜单；插入后使用普通组件编辑能力，不显示固定模块身份。
- 当前复制文案配置从模板编辑器隐藏；编辑器预览区直接展示系统按当前草稿自动生成的文案表格示例。
- fieldKey 默认收进高级设置，普通用户通过语义角色和令牌选择器配置业务用途。
- 编辑预览、新建派单和只读详情共用渲染器与布局计算函数。
- 校验错误定位到标签、区块和字段，并通过 aria-live 宣告。

有未保存修改时，切换模板、切换游戏、关闭或刷新页面都必须提示。

### 9.4 业务绑定与计算

- 人数来源使用明确选择器配置为固定人数、数字字段或可重复表格数量列汇总。
- 选择字段的每个选项可以独立打开价格调整并填写整数分；界面同时显示换算后的元，仅作展示。
- 所有绑定使用 stableKey，不把显示名称或用户可编辑的 fieldKey 当作业务关系。
- 删除被人数来源或其他业务规则引用的组件前必须阻止操作并提示先解除绑定。
- 禁用被引用组件时必须产生可定位校验错误，未修复前不能发布。

## 10. 新建派单交互

一个连续弹窗分为三个阶段：

1. 选择客户与游戏。
2. 选择该游戏的已发布模板。
3. 填写发布版本定义的通用表单，并创建草稿订单。

行为要求：

- 选择游戏后只展示该游戏的已发布模板。
- 优先选择游戏默认模板；没有默认时突出最近使用模板，但不自动提交。
- 模板卡片显示名称、说明、版本号、更新时间和最近使用状态。
- 表单标题显示游戏名、模板名和版本号。
- 普通字段、说明和可重复表格严格按发布快照渲染；页面不判断是否为岗位或段位模块。
- 人数和价格由服务端根据发布版本中的 staffingSource 与选项价格调整计算，前端只显示服务端返回的预览结果。
- 当前模板已有输入时，切换前必须提示；确认切换后把值缓存于本次弹窗会话。
- 切回原模板时恢复该模板在本次会话中的值。
- 没有已发布模板时展示空状态；有编辑权限的用户可跳转至带游戏筛选的模板管理页。
- 深链可记录 gameId 和 templateId，但客户隐私和表单值不得进入 URL。
- 提交期间禁用创建按钮，并使用 idempotencyKey 防止重复创建。
- 创建成功后的详情页展示自动文案表格和“复制派单文案”按钮；复制内容来自订单快照，不读取当前模板。

## 11. 数据流与异常

### 11.1 主数据流

- 编辑发布：选择游戏与模板 → 拉取通用草稿和 revision → 保存草稿 → 预览表单与自动文案 → 发布校验 → 创建版本 → 更新 activeVersionId。
- 创建派单：选择游戏 → 获取生效模板 → 锁定 templateVersionId → 加载通用表单 → 服务端按该版本校验并计算人数与价格调整 → 创建订单并保存快照 → 更新 lastUsedAt。
- 历史订单：始终读取订单自身快照，不依赖当前模板。
- 文案生成：订单详情读取自身快照和值 → 通用文案渲染器生成结构化表格与纯文本 → 用户复制；不维护逐模板字段映射。

### 11.2 异常处理

- 修订冲突返回 409，并保留用户输入。
- 模板填写期间被归档时，服务端拒绝创建；页面保留输入并提示重新选择可用模板，不静默改用其他模板。
- 版本不匹配时提示重新加载，不自动升级。
- 没有发布模板时禁止创建并给出配置入口。
- 发布校验返回可定位到具体区块和字段的结构化路径。
- 人数来源引用不存在、被禁用或类型不匹配时禁止发布，不回退到字段名称猜测。
- 选项价格不是整数分、超出范围或聚合策略不支持时禁止发布。
- 自动文案中遇到未知旧组件时保留安全占位并记录可观测错误，不执行任意表达式。
- 网络失败时保留页面内存中的草稿；敏感表单值不写入本地持久存储。
- 重复提交使用租户、用户和 idempotencyKey 返回同一创建结果。

## 12. 迁移与兼容

采用 expand-contract：

1. 已完成扩展：新增可空游戏归属、版本表、语义角色和索引；为现有模板生成版本 1。
2. 新增 S1b 扩展：使用新的向前迁移增加通用组件配置、可重复表格列、staffingSource 和选项价格调整；不得修改已经执行过的 S1 迁移。
3. 未归类：旧模板的 gameId 保持为空并进入“未归类”，不根据名称猜测。
4. 旧岗位：转换为“岗位与人数”通用可重复表格，并显式绑定人数列；原始数据保留到兼容审计完成。
5. 旧段位价格：优先与明确的 TARGET_RANK 语义字段选项匹配；无法无歧义匹配时保存为 legacyUnboundPriceRules 并标记“需要人工确认”，禁止猜测绑定后发布。
6. 旧复制行：旧发布版本和历史订单继续按旧快照读取；新编辑器隐藏 copyLines，新版本改用自动文案。不得改写历史快照。
7. 双读：通过功能开关让部分租户读取通用 v2；v2 订单写入版本标识和快照；旧接口保留只读兼容。
8. 人工归类与确认：管理员选择游戏、处理未绑定价格规则并预览自动文案后才能发布。
9. 收缩：活跃模板完成归类和兼容审计后，再评估移除旧 positions、rankRules、copyLines 写路径；数据库列的删除必须进入独立发布。

灰度期可以关闭 v2 读取开关。版本记录和订单快照保留，不执行破坏性回滚。数据库迁移执行及生产回退需单独授权。

## 13. 安全、审计与性能

### 13.1 安全与审计

- 所有读写强制租户过滤，并验证游戏、模板、版本的关联。
- 发布配置是派单验证的权威来源，客户端字段定义不可信。
- 动态输入执行控件类型、长度、选项、可重复行列和数值范围白名单校验。
- 通用组件类型、字段数量、区块数量、表格列数和提交行数均有服务端上限。
- 人数与价格只由服务端根据 stableKey 绑定和发布快照计算。
- 自动文案只输出经过纯文本转义和长度限制的显示值，不支持 HTML、脚本或任意表达式。
- 编辑、发布、恢复、设默认、归档、取消归档和删除记录审计事件。
- 审计包含操作者、租户、模板、修订或版本、时间和变更摘要。
- 自定义说明按纯文本显示。

### 13.2 性能

- 列表接口只返回摘要，详情按选中模板懒加载。
- 模板和版本使用游标分页。
- 新建派单只请求所选游戏的生效模板。
- 不可变发布配置可按 versionId 做租户隔离缓存。
- 避免列表阶段逐模板加载全部子表的 N+1 查询。
- 自动文案可以按订单快照哈希缓存，但缓存不是事实源，随时可确定性重建。

## 14. 测试策略

- 领域测试：状态转换、修订递增、默认唯一、通用组件校验、人数来源、选项价格聚合、自动文案、历史恢复和布局规则。
- 数据库集成：发布事务、乐观锁、版本号并发、租户隔离、索引、通用组件回填和旧数据兼容。
- API 合约：摘要边界、权限矩阵、结构化错误、409 冲突、组件引用、服务端金额计算和幂等。
- 端到端：多游戏筛选、添加两至五个不同区块、插入参考预设、禁用后恢复、保存草稿、发布、自动文案复制、派单、切换恢复、归档、历史订单和双人冲突。
- 无障碍：键盘排序、焦点管理、错误宣告和弹窗关闭后焦点恢复。

## 15. 验收标准

1. 新模板必须选择游戏，旧模板明确显示“未归类”。
2. 派单选择游戏后，只能看到该游戏有生效版本的模板。
3. 保存草稿不改变线上表单；发布后新表单才切换版本。
4. 订单保存 gameId、templateId、templateVersionId 和完整配置快照。
5. 字段改名不影响基于语义角色的业务规则。
6. 编辑器不再固定显示岗位席位、段位加价或复制文案模块。
7. 用户可以自由建立两至五个或更多通用区块，并通过参考预设快速生成可继续编辑的结构。
8. 区块和组件均有独立启用开关；禁用后配置保留，重新启用后恢复，删除必须为单独操作。
9. 岗位与人数预设最终保存为普通可重复表格，人数来源通过 stableKey 显式绑定。
10. 任意选择字段可以配置选项价格调整，服务端按发布快照计算，显示名称改变不影响结果。
11. 新模板不配置 copyLines；任意派单详情都能按订单快照生成文案表格和可复制纯文本。
12. 编辑器、预览、派单和自动文案对启用、必填、列宽、另起一行、表格行列和格式化规则解释一致。
13. 切换模板不会无提示丢失值，本次弹窗内可以恢复。
14. 旧修订保存返回 409，不覆盖其他管理员的修改。
15. 归档不破坏历史订单；只有未发布且未引用模板可硬删除。
16. Owner/Admin 默认可管理和发布，客服默认只能查看和使用。
17. 模板列表使用摘要和分页，不在列表阶段加载完整详情。
18. 迁移后旧模板都有版本 1，且不会被自动错误绑定游戏。
19. 旧岗位、价格和文案数据在兼容期可读取；无法无歧义绑定的价格规则必须人工确认，系统不得猜测。

## 16. 实施切片

### S1：领域模型与兼容底座

增加归属、状态、修订、语义角色、版本模型和迁移回填。证据为领域测试、迁移测试、租户隔离测试和回填报告。

### S1b：通用模板组件与兼容转换

新增通用组件、可重复表格、staffingSource、选项价格调整和自动文案领域模型；使用新的向前迁移转换旧岗位与可绑定的价格规则，并保留旧文案快照兼容。证据为转换测试、人数与金额规则测试、自动文案测试、租户隔离和回填审计。S1b 完成前不得进入 S2。

### S2：模板管理 API

实现摘要列表、通用草稿保存、发布、版本历史、恢复、复制和归档，并接入权限、审计、乐观锁、人数与价格服务端校验。证据为 API 合约、并发、金额和权限测试。

### S3：模板管理界面

实现按游戏管理、URL 状态、三标签通用编辑器、“添加内容”入口、参考预设、独立启用开关、自动文案预览、草稿与发布操作和版本历史。证据为组件测试、管理流程 Playwright 和键盘测试。

### S4：新建派单

实现客户与游戏、模板、通用表单三个阶段，以及可重复表格、服务端人数与价格计算、版本锁定、切换告警、会话缓存、幂等创建、订单快照和自动复制文案。证据为 API 集成测试与多游戏 Playwright 主路径。

### S5：灰度、观测与收缩

增加功能开关、指标和迁移审计，完成租户灰度、旧模板归类和旧路径移除评估。证据为灰度清单、回退演练和数据完整性报告。

## 17. 发布与回退

- 先在开发环境启用，再对测试租户启用，最后按租户逐步扩大。
- 观测模板列表延迟、草稿保存失败率、409 冲突率、通用组件校验失败、未绑定旧价格规则、自动文案生成失败、派单创建失败率和版本不匹配率。
- 灰度期间保留旧读取入口和 v2 功能开关。
- 回退优先关闭 v2 入口，不删除版本数据，不改写已创建订单。
- 生产启用必须在迁移审计、主路径端到端测试和回退演练通过后单独批准。

## 18. 已定边界

- 草稿保存与发布严格分离。
- 客服默认不可编辑或发布模板。
- 旧模板在人工归类前保持“未归类”。
- 每个游戏最多一个默认模板。
- 历史恢复先生成草稿，不直接上线。
