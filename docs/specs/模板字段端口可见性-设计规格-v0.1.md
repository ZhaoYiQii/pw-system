# 模板字段端口可见性 设计规格 v0.1

- 状态：**方向已获用户批准**（2026-09-18「b 先做吧」）；规格待审阅
- 日期：2026-09-18
- 范围：模板配置模型与校验（后端）、内容设计编辑器与渲染弹层（admin-web）、客户下单页（mobile）
- 非目标（本版明确不做）：陪玩端与老板端的字段渲染面（各自独立立项）；算价模型；发布设置屏

## 1. 背景与事实基线（已核实）

| 事实 | 证据 |
| --- | --- |
| 模板配置以 JSON 存储 | `game_dispatch_templates.draft_config_json`、`game_dispatch_template_versions.config_json` → **加属性零 DDL** |
| 后端用 **`z.strictObject`** 逐字段声明 | `apps/api/src/common/validation/api-validation-rules.ts:559,568,601,612,631` → **未知键被拒绝**（不是静默丢弃）。因此前端一旦发 `audiences` 而 schema 未更新，请求会直接 **400**；后端必须与前端**同批上线** |
| 现在真正渲染模板字段的界面只有两处 | ① 客服：`new-order-view.tsx` → `TemplateOrderForm`；② 客户：`apps/mobile/src/pages/customer/game-order`（读 `field.fieldKey` 拼 `formValues`） |
| 陪玩端不渲染模板字段 | `apps/mobile/src/pages/player/game-signup` 只显示「选择报名岗位」与岗位行 |
| 老板端无独立渲染面 | 老板复用商家端页面；订单详情显示快照文案，不是字段集 |
| `TemplateFormRenderer`（v1）无调用方 | 全仓 `rg` 仅命中自身定义 → 死代码，本版不动它 |

## 2. 决策

| 编号 | 决策 | 说明 |
| --- | --- | --- |
| V-1 | 端口矩阵本版只含**客服 / 客户** | 陪玩、老板各自的渲染面独立立项 |
| V-2 | 组件带 `audiences: ("CS" \| "CUSTOMER")[]` | 字段 / 表格 / 说明都带；**空数组非法**，至少一个 |
| V-3 | 分组带同样的 `audiences`，组件可覆盖 | 组件未显式声明时**继承分组**；显式声明即覆盖分组 |
| V-4 | **默认两个全选** | 新建组件/分组默认 `["CS","CUSTOMER"]`；用户可改 |
| V-5 | 语义 = **只有该端口的界面能看到并填写** | 未标记的端口看不到该字段，**也不记录它的值** |
| V-6 | 过滤的**权威在服务端** | 给客户端的接口只返回客户可见字段；前端过滤只是呈现，不作为安全边界 |
| V-7 | 渲染弹层改**两页**（客服 / 客户），左右滑动切换 | 两页都调用同一个过滤纯函数，保证预览与真身不会漂移 |
| V-8 | 历史模板无 `audiences` → 视为两个端口全选 | 行为与现在完全一致，不因上线改变既有模板 |

## 3. 数据形状（加性）

```jsonc
// 组件（FIELD / REPEATABLE_TABLE / NOTE）
{ "stableKey": "f1", "kind": "FIELD", "label": "客户手机号",
  "audiences": ["CS"],        // 新增；缺省 = 继承分组；分组也缺省 = 两个全选
  "fieldType": "TEXT", "required": true, "layout": { "colSpan": 1, "rowBreakBefore": false } }

// 分组
{ "stableKey": "s1", "label": "内部信息", "audiences": ["CS"], "columns": 2, "sortOrder": 0, "enabled": true }
```

## 4. 校验（服务端权威）

1. `audiences` 必须是数组、元素属于枚举、去重后**长度 ≥ 1**；不合法 → 400 并指明路径（沿用现有 issue 结构）。
2. 分组与组件各自校验；组件的合法性与分组无关（覆盖不等于豁免）。
3. 发布前在 `collectDraftIssues` 增加一条：某组件过滤后**两个端口都看不到** → 视为阻断项（实际由规则 1 已覆盖，此处作为双保险与更友好的提示）。
4. 草稿保存允许属性缺省（视为继承/全选），发布版本必须显式落地解析后的 `audiences`。

## 5. 数据流

1. 编辑器改标记 → 草稿（内存）→ 保存/发布 → 服务端校验 → 写入 `draft_config_json` / `config_json`。
2. 客服端（新建派单）：服务端返回的发布快照**按 CS 过滤** → `TemplateOrderForm` 渲染。
3. 客户端（H5 下单）：服务端返回的模板/订单数据**按 CUSTOMER 过滤** → 移动端渲染。
4. 渲染弹层：前端纯函数按当前页端口过滤，切页即换端口。
5. 下单写入：只接受并记录**该端口可见**的字段值。

## 6. 失败处理与边界

| 场景 | 处理 |
| --- | --- |
| 客户端提交了不可见字段的值 | 服务端**丢弃**该字段值（不报错），并在结构化日志留一条受控事件 |
| 两个端口都不给 | 保存/发布被拒（规则 1） |
| 历史模板无标记 | 回落"两个全选"（V-8） |
| 标记改动后的历史订单 | 订单快照**不动**；新单按新标记 |
| 分组被停用 | 沿用现有行为（不参与渲染），可见性不改变这一点 |

## 7. 测试与验收

- 纯函数单测：过滤（分组继承、组件覆盖、默认全选、历史模板回落、空数组拒绝）。
- 集成测试：保存/发布校验（空 `audiences` → 400）；发布版本落地解析后的值。
- 契约：新属性进入 OpenAPI → 需跑 `pnpm openapi:generate` 重生成 `openapi.yaml/json` 与 `packages/api-client`（**P1 授权动作**）。
- E2E：① 客服端只看得到 CS 字段；② 客户下单页看不到 CS-only 字段；③ 渲染弹层两页内容不同且可切换。
- 视觉基线：渲染弹层两页各一张快照。

## 8. 回滚

前端回退到旧编辑器；后端忽略新属性（旧模板本就不带）；**零 DDL、零数据迁移**。已发布的带标记版本仍可读（属性被旧代码忽略）。

## 9. 追加决策（2026-09-18 第二轮，开放问题已闭环）

| 编号 | 决策 | 说明 |
| --- | --- | --- |
| V-9 | **历史快照不动** | 标记改动只影响新单；已发生订单的字段与值一律不变（依赖既有订单快照机制） |
| V-10 | **可见性与必填互不影响** | 标记只管"看不看得见"，与必填无关，不新增任何耦合规则。推论：**必填只在可见的端口上生效**——客户看不到的字段，客户端不做必填校验；客服端照常校验 |
| V-11 | 渲染弹层**默认显示客服页** | 两页顺序为「客服 / 客户」，打开时停在客服 |
