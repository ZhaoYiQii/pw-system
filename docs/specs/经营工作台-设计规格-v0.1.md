## 1. 背景与目标

现状（已核对代码）：

- 商家端已有“工作台 / 记录台 / 监控台 / 门店设置”四组导航，默认落地页为 `/merchant-console/work`。
- 当前 WorkView 是“今日工作”：顶部问候 + 订单待办脉搏 + 待办订单表 + 待服务排班，数据来自 `/orders`、`/game-dispatch` 前端拉全量后过滤。
- 已存在但未聚合到首页的数据：进行中场次（`sessions`）、结算批次（`settlements`）、争议（`disputes`）、收入账本（`finance`/`ledger`）、异常提示（ai/risk 相关）。
- 商家端 UI 框架文档已规划“工作台 / 记录台 / 监控台”，本规格把默认落地页升级为“经营工作台”，而不是新建第四套导航。

目标：

1. 店老板/店长登录后，在第一屏就能回答三个问题：今天有什么必须处理？钱平不平？有什么风险？
2. 所有数字和待办都是“真实状态的投影”，点击后深链到现有记录页处理，不在首页再造一套管理逻辑。
3. 按角色裁剪内容，避免客服看到财务金额、财务看到一堆订单噪声。
4. 页面使用聚合接口一次返回，不再由前端并发拉全量列表。

## 2. 范围与非目标

范围内：

- 商家端默认落地页“经营工作台”的页面结构与角色裁剪设计。
- 后端新增只读聚合接口（建议归入主规格第 6.1 节的 `reporting` 模块职责）。
- WorkView 触达页面的新栈迁移与五态完善。
- 与聚合接口配套的集成测试、页面验收。

范围外（本规格不包含）：

- 任何订单/场次/账本/结算状态机改动。
- 新建“第四台”或重做监控台整体信息架构。
- 真实支付、分账、AI Provider、微信小程序。
- 首页的视觉风格重做（视觉如需另走 frontend-design）。
- 修改金额、租户绑定、权限后端模型或业务状态。

## 3. 设计决策（草案，逐条可推翻）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D-1 | 单一“经营工作台”作为全角色默认落地页，内容按角色裁剪 | 店长只需要一个首页；避免维护“今日工作”与“门店概览”两套首页 |
| D-2 | URL 保持 `/merchant-console/work`，模块 `work` 标签从“今日工作”改为“经营工作台” | 路由稳定、改动小；命名与销售语言一致 |
| D-3 | 新增后端只读聚合接口 `GET /api/v1/tenant/dashboard/summary` | 前端不再并发拉全量列表做统计；金额统计在服务端完成 |
| D-4 | 金额带（门店汇总金额）由服务端按角色裁剪后返回，不依赖前端隐藏；不影响客服查看其经手订单金额 | 前端隐藏不是授权；客服角色不接收门店汇总金额字段 |
| D-5 | “今日”按 Asia/Shanghai 自然日计算（已确认 v0.1）；门店时区能力就绪前不引入自定义营业日 | 口径简单、可解释；后续可扩展为 tenant 时区配置 |
| D-6 | 首页待办一律深链到记录台/监控台，不提供完整业务动作 | 单一事实源，避免状态分叉 |
| D-7 | v1 不展示“门店应收/实收/毛利”，金额位只放“待开通”占位；待收入账本切片落地后再接入 | 当前数据层没有可证实、可对账的门店收入分录，不能用订单快照或陪玩应付冒充收入（2026-09-10 拍板方案 A） |

## 4. 页面结构（经营工作台）

### 4.1 页面骨架

```text
┌───────────────────────────────────────────────────────────────┐
│ 门店名 · 2026/09/10           今日已服务 23 单 · 进行中 3 场   │
│                                [AI 录单] [新建派单]           │
├───────────────────────────────────────────────────────────────┤
│ 经营入账（应收/实收/毛利）待开通    结算待办 ¥2,100 · 4 笔    │  ← 金额位（v1 占位，财务可见）
├──────────┬──────────┬──────────┬──────────────────────────────┤
│ 待办订单  │ 进行中   │ 财务待办  │ 争议/异常                    │  ← 四块数字，点击直达
│   5 单    │  3 场    │  4 笔     │ 2 件                        │
├──────────┴──────────┴──────────┴──────────────────────────────┤
│ 需要处理（按优先级排序，每行一个动作）                           │
│ 01 派单 PW-… 三角洲  待选人        [去选人]                    │
│ 02 场次 S-… 已结束待确认           [去核对证据]                │
│ 03 批次 B-… 待复核                 [去复核]                    │
│ 04 争议 D-… 金额冻结               [去处理]                    │
├─────────────────────────────┬────────────────────────────────┤
│ 风险与提醒                    │ 快捷动作                       │
│ · 调整待复核 N                │ · AI 粘贴录单                 │
│ · 结算批次 open hold          │ · 登记收款 / 导入流水          │
│ · 争议冻结 N                  │ · 生成结算批次                 │
└─────────────────────────────┴────────────────────────────────┘
```

### 4.2 区域职责

| 区域 | 内容 | 动作 |
| --- | --- | --- |
| 顶部状态 | 门店名、日期、今日已服务单量、进行中场次 | “AI 录单 / 新建派单”快捷入口 |
| 金额位 | v1 只显示“结算待办（陪玩应付）金额/笔数”；应收/实收/毛利位标“待开通” | 点击进结算批次；不为不存在的收入指标显示 0 或假金额 |
| 数字带 | 待办订单、进行中场次、财务待办、争议/异常 | 每块可点击深链 |
| 需要处理 | 统一待办流（订单→场次→结算→争议按影响排序） | 每行只给一个主动作 |
| 风险与提醒 | 调整待复核、open hold、争议冻结、异常提示 | 点击进对应监控台 |
| 快捷动作 | AI 录单、登记收款、生成结算批次 | 高频动作 |

### 4.3 角色裁剪

| 区域 | TENANT_OWNER | TENANT_ADMIN | CUSTOMER_SERVICE | FINANCE |
| --- | --- | --- | --- | --- |
| 金额位（占位） | ✔ | ✔ | ✘ | ✔ |
| 待办订单 | ✔ | ✔ | ✔ | 可选收起 |
| 进行中场次 | ✔ | ✔ | ✔ | ✘ |
| 财务待办 | ✔ | ✔ | ✘ | ✔（默认定位） |
| 争议/异常 | ✔ | ✔ | ✔（仅自己可处理范围） | ✔（财务视角） |
| 风险与提醒 | 全量 | 全量 | 服务/争议相关 | 财务风险相关 |

> 前端裁剪之外，后端聚合接口必须按角色决定返回字段（尤其门店汇总金额字段）。
>
> 已确认口径（2026-09-10）：`CUSTOMER_SERVICE` 不接收“门店汇总金额”（今日应收/实收/余额类字段），但可查看自己经手订单的金额——报价与核价是客服工作的一部分，不因首页裁剪而失去订单级金额权限。

## 5. 关键口径（2026-09-10 已确认）

下列口径为 v0.1 实现基线：

| 口径 | v0.1 口径 | 说明 |
| --- | --- | --- |
| “今日” | Asia/Shanghai 自然日 `00:00:00+08:00 – 23:59:59+08:00` | 后续由 `tenant-config` 支持营业日再做扩展 |
| 今日已服务单量 | 今日“已结束或已确认”的场次对应订单去重数 | 建议以场次结束时间归类 |
| 门店应收/实收/毛利 | **v1 不实现**，页面占位“待开通” | 当前无门店收入分录事实源；由后续“收入账本”切片定义，禁止用订单快照或陪玩应付冒充 |
| 结算待办（陪玩应付） | `DRAFT/REVIEWED/APPROVED` 批次的 `totalAmountFen` 合计与笔数 | 仅 OWNER/ADMIN/FINANCE 可见；CS 不接收 |
| 待办订单 | 非终态且需要人动作的订单/派单 | `DRAFT/CONFIRMED/DISPATCHING/PENDING_CONFIRMATION` 等，以状态机为准 |
| 财务待办 | 非 `PAID/VOID` 的结算批次 + open hold | `DRAFT/REVIEWED/APPROVED` 一并与待确认/待支付区展示 |
| 争议/异常 | `OPEN` 争议 + 调整待复核 + 待确认场次 | v1 只统计可 SQL 确定的真实状态 |
| 风险提示 | 由真实状态推导，AI 建议后续叠加 | AI 异常只作为独立区块出现，不与钱字段混淆 |

> 若某指标无法用现有状态机准确推导，宁可先在页面隐藏/标注“待开通”，不得用近似算法展示成事实。

## 6. 后端聚合接口设计

### 6.1 端点

```http
GET /api/v1/tenant/dashboard/summary
```

- 认证：门店登录会话（owner/admin/cs/finance）。
- 租户：只允许当前 `TenantContext.tenantId`，禁止客户端传 tenantId。
- 只读：不产生事务写、不触发通知/审计外的只读审计（如有需要）。
- 套餐/角色：按角色裁字段；门店汇总金额字段对 `CUSTOMER_SERVICE` 不返回（订单级金额仍按既有权限返回）。

### 6.2 建议响应结构（草案）

```json
{
  "day": {
    "date": "2026-09-10",
    "tz": "Asia/Shanghai"
  },
  "metrics": {
    "todoOrders": 5,
    "liveSessions": 3,
    "financeTodos": 4,
    "openDisputes": 2,
    "riskAlerts": 1,
    "todayServiceCount": 23,
    "pendingSettlementCount": 4,
    "pendingSettlementAmountFen": "210000"
  },
  "attention": [
    {
      "id": "ord_1",
      "kind": "ORDER_TODO",
      "refType": "DISPATCH",
      "refId": "…",
      "refNo": "PW-…",
      "title": "三角洲护航 · 待选人",
      "subtitle": "客户昵称 / 状态",
      "priority": "HIGH",
      "action": "GO_SELECT",
      "occurredAt": "…"
    }
  ],
  "riskFeed": [
    {
      "id": "batch_1",
      "kind": "SETTLEMENT_TODO",
      "refType": "SETTLEMENT_BATCH",
      "refId": "…",
      "refNo": "B-…",
      "title": "结算批次待复核",
      "amountFen": "…",
      "priority": "HIGH",
      "occurredAt": "…"
    }
  ]

```

### 6.3 字段规则

- 金额字段一律 `string` 的“分”（如 `"846000"`），禁止 number。
- 接口级角色裁剪只针对**财务汇总字段**（`pendingSettlementCount`、`pendingSettlementAmountFen` 及 riskFeed 中的财务类金额）；订单级金额由既有订单/派单接口按既有权限返回，客服仍可查看经手订单金额。
- `refType/refId/refNo/action` 由后端给出；前端路由映射表负责拼深链，不在后端写死 URL。
- `attention` 是合并排序的“当前需要动作”列表：订单待办、待确认/调整场次、待复核/待批准/待支付批次、开放争议；排序按“影响 > 发生时间”，v1 允许简单按时间倒序 + 类型权重。
- `riskFeed` v1 为真实状态推导；`aiAnomaly` 建议等 AI Provider 就绪后再以独立字段接入，不与 metrics 混算。
- 后端返回前按角色删除财务汇总字段；CS 请求时 `pendingSettlementCount/pendingSettlementAmountFen` 直接缺省，页面按“无权限”展示而不是渲染 0。

### 6.4 聚合来源与性能约束

- 查询只读取订单/派单/场次/结算/争议的现有状态字段，并遵守 RLS。
- v1 不实现门店应收/实收；后续“收入账本”切片必须先与 ledger/wallet/结算实现核对并定义收入分录，禁止用订单价快照当作实收。
- 首版允许按 tenant + 当日时间范围走现有索引做只读统计；若超过容量基线（100 租户 / 100 万历史订单），再评估 `reporting` 预聚合表。
- 接口必须返回空态（门店没有任何数据时返回 0 与空列表），不允许 404。

## 7. 前端改动设计

建议修改文件（最终以实施计划为准）：

- `apps/admin-web/app/_lib/merchant-console/work-view.tsx`：重写为经营工作台，消费新聚合接口；若沿用 `mc-*` 旧样式，按 G4 规则一次迁移到 Tailwind v4 + shadcn/ui + TanStack Query。
- `apps/admin-web/app/_lib/merchant-console/modules.ts`：`work` 模块标签改为“经营工作台”；增加角色默认首页来源。
- `apps/admin-web/app/_lib/merchant-console/merchant-api.ts`：新增 `DashboardSummary` 相关类型与 API 调用。
- `apps/admin-web/app/_lib/merchant-console/merchant-shell.tsx`：品牌区与登录后跳转仍指向 `/work`，无需新增路由。
- 前端路由映射：`refType + action → /merchant-console/{dispatch|sessions|settlements|disputes|finrisk|...}` 的单一映射表。

页面行为要求：

- loading / empty / error / offline-retry / 403 五态完整。
- 数据刷新：使用 TanStack Query，staleTime 15s；页面聚焦时重取；金额与待办不依赖长连接轮询。
- 每个待办行只保留一个主动作；按钮文案与动作结果一致（“去复核”而不是“提交”）。
- 数字与金额使用等宽数字；差额非零用语义色，不臆造“赚/亏”结论。
- 金额与状态以服务端为准；接口失败时不显示缓存旧金额冒充实时。

## 8. 验收与证据

### 8.1 后端

- 集成测试：owner/admin/cs/finance 四角色访问同一 endpoint，返回字段按角色裁剪；CS 不含金额字段。

- `@pw/admin-web` typecheck / lint / build 通过（真实命令输出）。

- 打开页面无控制台错误、无横向溢出；键盘可完成主操作。
