# 算价模型 设计规格 v0.1（订单定价 · 报单时长 · 应收/实收）

- 状态：**产品口径已确认（2026-09-20），待批准进入实施计划**（本文件只是设计，不含实现）
- 日期：2026-09-20（同日修订一次）
- 变更记录：2026-09-20 按用户对原第 9 节五条待确认项的答复修订——报名界面显示**单价**（不乘时长）；**固定价本版不做**（改由客服在派单时填写，后续单独立项）；选中后不可自助取消、放鸽子记违约并通知老板；报单证据复用现有通道；申报时长为计费依据。
- 范围：订单定价（陪玩×游戏底价、按游戏的加价规则库）、陪玩报单（申报时长 + 截图证据）、老板支出/陪玩实收/门店毛利口径、报名与自动关单交互
- 非目标（本版明确不做）：**固定价（FIXED）规则**——后续单独立项，由客服在派单时填写，老板不填；平台抽成（置 0，公式不动）；真实支付渠道；结算批次流程本身（沿用 P5 既有实现）；陪玩端与老板端字段渲染面的其它改造

## 1. 背景与现状（已核实）

算价并不是从零开始，现有实现已覆盖大半，但**分散在两套机制里**：

| 能力 | 现状 | 位置 |
| --- | --- | --- |
| 陪玩底价 | `PlayerProfile.basePricePerHourFen`——**每个陪玩一个价，不区分游戏** | `packages/database/prisma/schema.prisma` |
| 段位加价 | 经典派单选人时用模板快照的 `rankRulesJson`（`rankLabel → addPriceFen`） | `apps/api/src/modules/game-dispatch/application/game-dispatch.service.ts` |
| 选项加价 | 通用模板下单时用模板字段选项的 `addPriceFen`（SUM/MAX） | `apps/api/src/modules/game-dispatch/domain/game-template-calculations.ts` |
| 选人计价 | `单价 = 底价 + 命中加价`，写入 `OrderSlot.unitPriceFen` 快照，并按 `单价 × 时长 / 60` 校验老板钱包 | `game-dispatch.service.ts` |
| 抽成 | `splitSettlement()`：平台费 bp + 门店抽成 bp，尾差归陪玩 | `apps/api/src/modules/ledger/domain/split.ts` |
| 费率 | `FinanceRateRule`（每租户一条，默认平台 300bp / 门店 2000bp） | `schema.prisma` |
| 记账 | `SlotEarning`（陪玩应收）→ `LedgerEntry` → `SettlementBatch`/`SettlementItem` | `schema.prisma` |
| 时长 | `SlotSession.startedAt/endedAt/durationSeconds`——由开始/结束证据计时 | `schema.prisma` |
| 证据 | `SlotEvidence`（对象存储 key + sha256 + mime），已有开始/结束证据位 | `schema.prisma` |
| 报名/取消 | `POST .../applications`、`POST applications/:id/withdraw`、`DELETE applications/:id` | `game-dispatch.controller.ts` |
| 定时任务 | 后台 worker 有 tick（超时自动确认完成核算、订阅到期回收），**无无人报名自动关单** | `apps/api/src/background/worker.ts` |

**主要问题**：加价规则存在两条并行路径（模板快照的段位加价 / 字段选项加价），同一笔订单的钱可能由两套规则各算一半；底价不区分游戏，与"陪玩在不同游戏定价不同"的现实不符。

## 2. 已确认的产品决策（2026-09-20 用户确认）

1. **时长来源**：陪玩结束服务时在**报单表**填写总时长，并上传**开始/结束时间截图**作为证据，用于后续人工核查，防止乱填。
2. **底价维度**：底价按**陪玩 × 游戏**隔离（一个陪玩可以接多个游戏，每个游戏定价不同）。
3. **规则库**：把加价规则做成**独立的、按游戏绑定的定价规则库**；本版只实现**加价（SURCHARGE）**，固定价后续单独立项（由客服在派单时填写）。
4. **抽成口径**：平台费暂时取消（费率置 0，公式不改）。`订单金额 = 陪玩实收 + 门店抽成`，`门店毛利 = 订单金额 − 陪玩实收`。
5. **展示口径**：报名界面显示**单价**（老板与陪玩看到同一个数字，**不乘时长**）；**实际到手**在陪玩结束服务报单时才显示。无人报名默认 **5 分钟自动关单**、可配置。

## 3. 目标模型

### 3.1 定价三要素

1. **底价 `player_game_prices`**（陪玩 × 游戏，分/小时）：某陪玩在某游戏的底价。
   - 现有 `PlayerProfile.basePricePerHourFen` 保留为**兜底**：该陪玩在该游戏没有专属底价时使用，避免一次性重写历史数据。
2. **定价规则库 `game_pricing_rules`（按游戏绑定）**：规则项首期只有一类——`SURCHARGE`（加价，分/小时，≥ 0）。
   - `FIXED`（固定价）**本版不实现**，但规则项保留类型字段与校验位，供后续切片接入，避免二次迁移。
   - 规则库是**唯一权威**：模板快照与模板字段选项不再持有价格（见 §5 迁移）。
3. **抽成 `FinanceRateRule`**：全店一条门店抽成 bp；`platformFeeBp` 置 0。

### 3.2 金额公式（全整数分，向上取整到分）

```
单价(陪玩, 游戏, 段位) = 底价(陪玩×游戏, 缺省用兜底) + Σ 命中的加价        // 本版无固定价
订单金额（老板支出/应收） = Σ 每个已确认名额 ( 单价 × 申报时长分钟 / 60 )   // (price*minutes+59)/60
门店抽成               = 订单金额 × storeCutBp / 10000
陪玩实收               = 订单金额 − 门店抽成        // 平台费为 0，尾差归陪玩
门店毛利               = 订单金额 − 陪玩实收 = 门店抽成
```

订单的**默认时长 60 分钟**，用于下单/选人时的估算与老板钱包余额校验；最终金额以报单的申报时长为准。

### 3.3 时长与报单

- 报单表（陪玩端）：**总时长（分钟，必填）** + 开始时间截图 + 结束时间截图。
- **申报时长是计费依据**；截图证据进入 `SlotEvidence` 通道（复用现有对象存储 + sha256），供人工核查。
- 商家确认/结算环节**可修正时长**，修正需记录事件与理由（审计）。
- 与现有证据计时并存：`SlotSession.durationSeconds` 保留为对照；申报时长与证据计时差异超过阈值时，标记该单"待核查"（只标记，不阻断）。

### 3.4 展示口径

| 界面 | 显示 | 口径 |
| --- | --- | --- |
| 报名详情（老板端 / 陪玩端） | **单价**（分/小时，同一数字） | `底价 + 命中加价`，**不乘时长** |
| 陪玩报单后 | **最终到手（实收）** | 结算时实时算 |
| 商家端订单/工作台 | 支出、抽成、门店毛利 | 结算时实时算 |

### 3.5 报名与关单

- 陪玩端：**报名** / **取消报名** 两个按钮（未选中前可自助取消；后端接口已存在，补前端与状态规则）。
- **选中（老板锁定）后不可自助取消**：只能由商家"释放名额"后重新开放报名。
- 若陪玩实际未到场/放鸽子：由商家记录**违约**并触发**通知老板**（复用现有通知模块）。
- **无人报名**：默认 5 分钟自动关单（可配置），复用后台 worker tick；老板也可主动取消订单。

## 4. 候选方案与取舍

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | 新增陪玩×游戏底价表 + 独立按游戏加价规则库；模板不再持有价格 | 与业务事实一致；规则可改、即时生效；只有一套权威 | 需要迁移与一次性改造两处现有价格来源 |
| B | 保留模板快照 `rankRulesJson`，仅做字段扩展 | 改动最小 | 仍按模板/快照生效，改规则要重发模板；双轨继续存在 |
| C | 继续把规则塞进模板字段选项 | 不动数据模型 | 价格与表单结构耦合，无法表达"整游戏定价"，且已有两套并存 |

选 A。理由：本次目标本身就是"按游戏隔离定价"，而 B/C 的载体（模板/字段选项）不是游戏维度；且两条并行路径必须收成一条，否则金额口径无法审计。

**固定价（FIXED）**：本版不做。它是"客服在派单时给某些陪玩/游戏填一个固定价"的另一条产品线（老板不参与填写），与本次的"底价+加价"是并列关系而非包含关系，单独立项更清晰；规则项保留类型位，届时不需要二次迁移。

## 5. 数据模型与迁移

**新增**

- `player_game_prices`：`tenantId, playerId, gameId, basePricePerHourFen, effectiveFrom?, status`，唯一键 `(tenantId, playerId, gameId)`。
- `game_pricing_rules` + `game_pricing_rule_items`：`tenantId, gameId` 唯一；规则项 `kind(SURCHARGE|FIXED), rankLabel?, amountFen`（本版只写入 `SURCHARGE`）。
- `player_breach_records`：`tenantId, playerId, orderId, orderSlotId?, reason, recordedBy, createdAt`（放鸽子违约记录，供后续统计与通知）。
- `slot_sessions.declared_duration_minutes`（申报时长）、`slot_sessions.duration_flagged`（待核查标记）。

**迁移（幂等脚本）**

1. 把各游戏的模板快照 `rankRulesJson` 归并为该游戏的 `SURCHARGE` 规则项（同游戏同段位取最新快照值）。
2. 把模板字段选项里的 `addPriceFen` 一并归并（若与快照冲突，以快照为准，并在迁移报告里列出）。
3. 旧字段（`rankRulesJson`、选项 `addPriceFen`）**不删除**，标为 legacy 只读，保留一个版本的兼容期。

**回滚**：新表可停用并回退到旧字段读取；旧字段未删除，回滚不涉及数据丢失。

## 6. 失败处理与边界

- 既无底价（含兜底）也无命中规则 → **拒绝报名/选人**并返回明确业务错误，不静默按 0 计。
- 选中后陪玩自助取消 → 返回受控 409（`APPLICATION_LOCKED`），提示走商家释放名额。
- 重复报名 / 已关单后报名 → 受控 409（沿用现有报名冲突语义）。
- 申报时长边界：15–1440 分钟（延续现有校验），超界拒绝。
- 关单与报名并发：以状态机 + 行锁保证只有一方成功。
- 金额一律 bigint 分，禁止浮点；尾差归陪玩（沿用 `splitSettlement`）。

## 7. 影响面

- **API/契约**：新增陪玩×游戏底价、规则库读写、报单提交/修正、违约记录与释放名额；`openapi:check` 需同步重生成。
- **前端**：陪玩端报单表与报名/取消按钮；老板端报名详情的单价；商家端规则库编辑页与违约记录入口。
- **账本**：沿用 `SlotEarning`/`LedgerEntry`/`SettlementBatch`；费率平台位 = 0。
- **通知**：陪玩放鸽子违约后通知老板（复用现有通知模块）。
- **权限**：规则库仅店主/管理员可写；陪玩只能看到自己的命中结果（自己的底价 + 规则命中后的单价、实收）。
- **兼容**：CLASSIC 旧流程按 ADR-0002 冻结，本设计只作用于 game-dispatch 主线。

## 9. 已确认清单（原待确认项，2026-09-20 答复）

1. 报名界面显示**单价**（分/小时，不乘时长），老板与陪玩看到同一数字；订单**默认时长 60 分钟**用于估算与余额校验。
2. **固定价本版不做**：它由客服在派单时填写（老板不参与），后续单独立项；规则项保留类型位。
3. 老板选中锁定后**陪玩不可自助取消**；人工放鸽子记**违约**并**通知老板**。
4. 报单的开始/结束截图**复用现有证据通道**（`SlotEvidence`，对象存储 + sha256），新增"报单"用途标识。
5. **申报时长为计费依据**；证据计时仅作核查对照。

仍按建议保留的一条（若不需要请说一声）：申报时长与证据计时相差超过 15 分钟或 20% 时，把该单标记为"待核查"，只标记不阻断。
