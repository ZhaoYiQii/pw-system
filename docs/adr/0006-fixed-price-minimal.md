# ADR-0006：固定价（FIXED）最小版

- 状态：**已批准**（用户 2026-09-21「按你的推荐」，与 P3 其余三项同批）
- 日期：2026-09-21
- 关联：算价模型设计规格 §2/§4/§9 第 2 条；ADR-0003（定价公式）、ADR-0004（档位分摊）

## 背景

- 设计规格明确：**固定价本版不做**，「它由客服在派单时填写（老板不参与），后续单独立项；规则项保留类型位」。
- 现状：定价只实现 SURCHARGE；`order_slots.unit_price_fen` 是选人时落下的单价快照（bigint 分）。
- 若不立项：客服线下议价无法进入系统 → 老板端看到的「单价」与最终结算（底价 + 加价）可能不一致，报单审批时按算法价结算会与谈好的价对不上。

## 候选方案

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 不立项 | 保持现状，靠线下沟通 | 零改动；但「展示单价」与「结算金额」可能不一致，缺少审计 |
| **B 最小版（选）** | 选人时可选填「本单固定价」，覆盖该档位单价快照；跳过加价；允许低于底价（二次确认 + 审计） | 与规格定位一致；不改表结构（快照列 + 审计即可）；不引入规则库新语义 |
| C 规则库形态 | 把 `FIXED` 做成规则项类型（陪玩×游戏×维度，可预维护、批量） | 表达力更强，但要新定义 FIXED 与加价的优先级/互斥，且与「派单时填写」的定位不符 |

选 **B**。

## 决策

1. 固定价由**商家端选人**填写（客服/店主，`gameDispatch.manage`）；**老板端自助选人接口不读取**该字段（请求体只取 `applicationIds`，多余的 `fixedPrices` 被忽略且不报错，契约用例断言单价不变）。
2. 固定价**即最终单价**（分/小时），跳过底价与加价计算，写入 `order_slots.unit_price_fen` 快照；展示与结算都使用它。
3. 允许低于底价：前端二次确认，后端写审计 `game_dispatch.slot_fixed_price`（含 `from`/`to` 与可选理由）。
4. 校验：整数分，范围 `1..1000000` 分/小时；越界 400；应用不属该单或非 `APPLIED` → 409；`fixedPrices` 含未在本次 `applicationIds` 内的报名 → 400。
5. 选人时的余额预估使用固定价（不再用算法单价）。
6. **不改表结构**：复用 `order_slots.unit_price_fen` 与 `audit_logs`；`kind=FIXED` 的类型位继续保留给未来的规则库形态（本次不写入）。
7. 结算公式不变：`固定价 × 申报分钟 / 60` 向上取整；`SlotEarning.amountFen` 仍是陪玩实收（ADR-0004）。

## 影响面

- 契约：`POST /api/v1/tenant/game-dispatch/orders/{orderId}/assignment` 新增可选 `fixedPrices[]`；`openapi` 需重生成。
- 后端：`game-dispatch.service.ts` 的 `assign`（校验、快照、余额预估、审计）。
- 前端：商家端派单/选人界面新增固定价输入（含二次确认）。
- 用例：单测（解析/边界）、集成（快照、结算、余额、审计、越权）、契约、E2E。
- 权限：不新增权限位；沿用 `gameDispatch.manage`。

## 回滚

回退代码即可。已产生的固定价快照保留在 `order_slots.unit_price_fen`（历史事实，无需清洗）；回退后新单不再接受该字段。
