# ADR-0007：租户仓库方法首参必须是租户上下文

- 状态：**已批准**（用户 2026-09-22「按你的建议继续做完」；本轮只落文档，不改代码）
- 日期：2026-09-22
- 关联：主规格 §8.1/§8.2（RLS 与租户隔离）、`apps/api/src/common/database/tenant-guard.ts`

## 背景

- 多租户隔离靠两层：Postgres RLS 策略 + 每次租户数据访问都被 `withTenantContext` 包在事务里执行 `set_config('app.tenant_id', ...)`。
- `tenantGuarded()` 用 Proxy 自动完成这件事：它从「方法第一个参数」推断 tenantId——字符串直接用，对象取 `.tenantId`。
- 但它留了一个**直通分支**（`tenant-guard.ts:36-42`）：当首参既不是字符串、也不含 `tenantId` 时，直接 `Reflect.apply` 执行原方法，**不进 `withTenantContext`**。该分支是为平台域/系统调用准备的，但触发条件是「首参形状」，不是显式意图。
- 现状：20+ 个仓库/服务被 `tenantGuarded` 包装（ledger、orders、sessions、dispatch、players、customers、catalog、wallet、tenant-config、reporting、game-dispatch 全家、entitlements 等）。
- 因此新增仓储方法时，如果第一个参数不是 tenantId（例如先传 orderId，或传一个不含 `tenantId` 的 DTO），该方法会**静默失去 RLS 上下文**：没有编译错误、没有测试失败，只会在真机上表现为「能读到别家数据」。

## 约束

- 不做投机性加固；本轮不引入默认拒绝之外的隐式行为变化。
- 平台域确实需要跨租户访问（平台开店、平台审计、平台费率等），因此不能简单把直通分支改成抛错。

## 候选方案

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 加固代码 | 直通分支改为抛错，另建显式白名单 API 给平台调用方 | 理论最强；但要逐个改造 20+ 包装点的平台调用路径，改错会让平台功能直接 500。审计阶段未构造出可利用路径，收益不可测 |
| **B 只写不变量（选）** | 把「首参必须是租户上下文」写成 ADR 作为 review 依据；不改代码 | 零行为风险；把隐式约定变成显式约束 |
| C 不记录 | 什么都不留 | 下次仍会有人按签名顺序无意踩中 |

选 **B**。

## 决定

1. **不变量**：任何被 `tenantGuarded` 包装的仓库/服务，其方法**第一个参数必须是**租户上下文字符串，或一个**含 `tenantId` 字段**的对象。需要别的首参时，把 tenantId 提到第一位，或改成 `{ tenantId, ...其余 }` 形状。
2. **平台/系统直通必须是显式意图**：不得依赖「首参恰好不是租户上下文」获得直通；确需跨租户执行的方法，必须在命名或注释里显式标注，并在 review 时说明为什么可以绕过 RLS。
3. **新增方法自查**：签名首参是不是 tenantId？若不是，调用点是否已通过别的方式设好 `app.tenant_id`？
4. 本轮**不改** `tenant-guard.ts`。

## 理由

- 审计阶段用两条独立路径尝试构造「因首参形状丢失 RLS」的可达越权路径，**均未成功**；没有可复现利用路径时修改安全关键代码属于投机性改动。
- 该风险的真正形态是「未来的方法签名变化」，而 ADR + review 恰好约束那个时刻。

## 影响

- 行为：无变化（纯文档）。
- 流程：新增/修改仓储方法时多一条 review 依据；平台直通调用需显式标注。
- 迁移方式：无。回滚方式：删除本 ADR。

## 验证证据

- 直通分支：`apps/api/src/common/database/tenant-guard.ts:36-42`。
- 包装点：`rg -n "tenantGuarded\(" apps/api/src` 命中 20+ 处。
- 可利用性：**未验证**——未能构造可达越权路径，故本 ADR 记录的是机制风险与预防性约束，不是已确认漏洞。
